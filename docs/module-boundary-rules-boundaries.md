# Module Boundary Rules Boundaries

Phase: 112B - MODULE BOUNDARY RULES PLAN

Status: boundary plan / docs-only

## Purpose

This document defines safety boundaries for the future Module Boundary Rules
layer. The layer should describe dependency policies and import concerns as
metadata only. It must not become a repo scanner, refactor engine, runtime
gate, dashboard adapter, provider bridge, or enforcement system.

## Posture

The future module boundary layer should remain:

- report-only,
- advisory-only,
- source-only,
- metadata-only,
- deterministic from caller-provided context,
- no scanner implementation,
- no refactor implementation.

## Forbidden Behavior

The layer must not:

- scan files,
- walk the repository,
- parse source imports automatically,
- rewrite imports,
- move modules,
- launch processes,
- read environment values,
- call networks,
- call providers,
- mutate dashboards,
- operate OpenClaw,
- send WhatsApp messages,
- run n8n,
- persist memory,
- mutate stores,
- mutate DB or SQL files,
- deploy,
- change package scripts,
- change workflows,
- perform source-control behavior from source.

## Import Boundaries

Future boundary-rule source should stay inside `src/architecture`.

Allowed in 112I:

- local architecture imports,
- type-only PM imports for evidence and risk vocabulary if needed,
- static constants and metadata-only helpers.

Disallowed in 112I:

- PM state mutation,
- Autopilot invocation,
- runtime imports,
- dashboard imports,
- provider imports,
- integration imports,
- WhatsApp imports,
- Viernes bridge imports,
- action/job/automation imports,
- config or credential imports,
- DB/SQL imports,
- deployment imports.

## Layer Map Boundary

A future layer map should be static metadata supplied in source. It should not
be generated by scanning directories in Phase 112I.

Layer map entries should describe:

- module reference id,
- layer,
- safe summary,
- allowed target layers,
- forbidden target layers,
- metadata-only flags.

## Finding Boundary

Boundary findings are architecture review metadata. They are not:

- build errors,
- runtime gates,
- refactor commands,
- dashboard events,
- provider actions,
- job requests,
- approval records,
- deployment checks.

Any future enforcement requires a separate phase with explicit approval,
rollback strategy, and verification.

## PM Boundary

PM may consume boundary findings as report/risk/blocker/next-action context.
Boundary rules must not mutate PM state or invoke PM report builders by
themselves.

## Autopilot Boundary

Autopilot may receive boundary findings as context in a future handoff or
closeout. Boundary rules must not trigger handoff, validation, memory
persistence, next-action coordination, or closeout.

## Dashboard Boundary

Dashboard must remain isolated. Module boundary metadata may be displayed in a
future read-only surface only after a dedicated dashboard plan exists.

## Stop Conditions For 112I

Phase 112I should stop and request review if the implementation would require:

- scanning source files,
- import parsing,
- source rewriting,
- runtime hooks,
- provider calls,
- dashboard changes,
- package changes,
- workflow changes,
- external automation,
- DB/SQL mutation,
- deployment behavior,
- real refactors outside the planned files.
