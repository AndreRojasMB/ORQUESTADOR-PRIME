# Module Boundary Rules

Phase: 112I - MODULE BOUNDARY RULES IMPLEMENTATION

Status: source-only / report-only / advisory

## Purpose

The Module Boundary Rules layer defines source-only metadata for architecture
layer ownership, import policies, boundary findings, and static layer maps.

The layer does not scan the repository, parse imports, rewrite source, perform
refactors, launch processes, call providers, mutate dashboards, operate
OpenClaw, send WhatsApp messages, run n8n, persist memory, deploy, mutate
DB/SQL, or perform source-control behavior from source.

## Implemented Source Files

- `src/architecture/moduleBoundaries.ts`
- `src/architecture/layerMap.ts`
- `src/architecture/index.ts`

## Module Layers

Implemented layer values:

## Import Policies

Implemented policy values:

- `allowed`
- `allowed_type_only`
- `review_required`
- `forbidden`
- `future_gated`

Policies describe review posture only. They do not fail builds, enforce CI, or
rewrite imports.

## Finding Model

A module boundary finding includes:

- finding id,
- source module reference,
- target module reference,
- source layer,
- target layer,
- import path metadata,
- import kind,
- policy,
- severity,
- description,
- evidence references,
- suggested action,
- risk level,
- approval metadata,
- PM escalation metadata,
- Autopilot use metadata,
- source-only boundary flags.

Findings are not refactor commands.

## Layer Map

`src/architecture/layerMap.ts` defines a static default layer map. It includes
allowed targets, review-required targets, forbidden targets, future-gated
targets, and rationale for each layer.

The map is static metadata. It is not generated by scanning directories.

## Helpers

Implemented pure helpers:

- `createModuleBoundaryFinding(...)`
- `classifyImportPolicy(...)`
- `describeModuleLayer(...)`
- `summarizeModuleBoundaryFindings(...)`
- `buildDefaultLayerMap(...)`

Helpers operate only on caller-provided metadata and static layer metadata.

## SOLID Integration

Module boundary findings support SOLID work:

- SRP through clear layer responsibility.
- OCP through extension boundaries.
- DIP through core/infrastructure separation.
- ISP and LSP through future contract-focused checks.

The module boundary layer does not execute SOLID refactors.

## PM Integration

Boundary findings may later feed:

- PM Status Reports,
- PM risk metadata,
- PM blocker metadata,
- Next Best Action recommendations,
- phase closeout summaries.

This is context only. The module boundary layer does not mutate PM state or
invoke PM builders.

## Autopilot Integration

Boundary findings may be passed as context to future handoff, validation, or
closeout metadata.

They do not start handoff runners, validators, memory persistence, next-action
coordination, or closeout coordination.

## Limitations

Phase 112I intentionally does not include:

- repository scanning,
- import parsing,
- dependency graph extraction,
- refactor execution,
- import rewriting,
- runtime gates,
- dashboard display,
- provider integration,
- persistence,
- package scripts,
- workflow integration.
